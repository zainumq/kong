## Temuan Medium

### M-1 — `graduate()` mengabaikan nilai balik `addLiquidity`: dana escrow bisa terkunci bila pool sudah ada dengan rasio menyimpang

**Lokasi:** `src/KongSale.sol:366-376` (`graduate()`)

**Penjelasan:**
`graduate()` memanggil `router.addLiquidity(kong, usdt, 250M, liquidityUsdt, 0, 0,
LP_BURN, block.timestamp)` dan mengabaikan nilai balik `(amountA, amountB,
liquidity)`. Router UniswapV2/PancakeSwap V2 hanya menarik jumlah *optimal*
berdasarkan rasio cadangan pool yang sudah ada — bila pair KONG/USDT sudah
memiliki likuiditas dengan rasio berbeda dari 250M : 12.600 USDT, router hanya
menarik sebagian dari jumlah yang diinginkan dan sisanya tertinggal di kontrak
sale. Karena tidak ada fungsi withdraw/rescue (by design) dan `sweepUnclaimed()`
revert setelah graduation, sisa tersebut **terkunci selamanya**. Event
`Graduated` juga tetap mencatat `liquidityUsdt` penuh (12.600 USDT) meski yang
benar-benar masuk pool lebih kecil — salah catat.

**Dampak:**
- Arah skew 1 (pool menghargai KONG terlalu tinggi): router menarik semua KONG
  tapi hanya sebagian USDT → sisa USDT (dalam PoC: 6.300 USDT, ekstremnya
  mendekati 12.600 USDT) terkunci di sale. Itu dana escrow user.
- Arah skew 2 (pool menghargai KONG terlalu rendah): router menarik semua USDT
  tapi hanya sebagian KONG → sisa KONG (ekstremnya mendekati 250M) terkunci;
  pool yang terbentuk sangat kecil sehingga token praktis tanpa likuiditas.
  Klaim pass (485M) dan referral tetap terbayar karena diambil dari saldo yang
  sama, tapi likuiditas awal hancur.
- Prasyarat: pair KONG/USDT dengan likuiditas harus sudah ada sebelum
  `graduate()`. Itu mensyaratkan KONG beredar sebelum graduation — saat ini
  hanya deployer (50M KONG komunitas) yang memegang KONG likuid. Pihak luar
  **tidak bisa** memicu ini sendiri. Skenario realistisnya adalah kesalahan
  operasional deployer (mis. mengirim KONG komunitas ke market maker lebih
  awal, atau membuat pool uji coba), atau kompromi kunci deployer.
- Catatan: membuat pair *kosong* via `createPair` saja TIDAK memicu ini —
  `addLiquidity` pada pair kosong memakai rasio penuh sesuai jumlah yang
  diminta.

**PoC:** `test_PoC_SkewedPoolLocksExcessUsdt` (lihat Lampiran A) — router mock
yang mensimulasikan pool menyimpang (menarik semua KONG, setengah USDT):
`graduate()` sukses, 6.300 USDT tertinggal di sale, `sweepUnclaimed()` revert
`AlreadyGraduated`. ✅ PoC lolos.

**Rekomendasi:**
1. **Operasional (wajib, sebelum 1 Des):** jangan memindahkan 50M KONG
   komunitas ke siapa pun dan jangan membuat pool KONG/USDT (atau pair di DEX
   mana pun) sebelum `graduate()` berhasil. Cantumkan ini di checklist launch.
2. Untuk deploy berikutnya: assert nilai balik —
   `require(amountA == LIQUIDITY_ALLOCATION && amountB == liquidityUsdt)` —
   agar graduation gagal total (dan bisa dicoba lagi) daripada sukses setengah.
   Alternatif: buat pair + tambah likuiditas dalam dua langkah dengan verifikasi
   cadangan pool sebelum memanggil `addLiquidity`.
3. Pertimbangkan fork test melawan router PancakeSwap asli sebelum launch
   (lihat L-3).

## Temuan Low

### L-1 — `mintPass` tanpa proteksi slippage: `quote()` tidak mengikat, pembeli bisa membayar sampai 50% lebih mahal bila di-front-run melewati batas tier

**Lokasi:** `src/KongSale.sol:299-347` (`mintPass`), `:263-268` (`quote`)

**Penjelasan:** `mintPass(amount, referrer)` tidak punya parameter harga
maksimum atau deadline. Harga ditentukan oleh nomor share *saat eksekusi*.
Pembeli yang mengutip harga lalu transaksinya tertunda/didahului melewati batas
tier (2.500 / 6.000) akan membayar harga tier berikutnya tanpa peringatan.
Tidak ada cara on-chain bagi pembeli untuk membatalkan bila harga bergerak.

**Dampak:** terbatas — melewati satu batas tier = maksimal 10 share × 0,5 USDT
= **5 USDT** lebih mahal per transaksi, plus pass yang diterima bertier lebih
rendah (kehilangan 10.000 KONG claimable per share, ~$5 pada harga buka pool).
Tidak ada pencurian; pembeli tetap menerima pass. Skenario realistis: bot
membeli sisa share Tier 1 saat pembeli lain mengantre di dekat batas 2.500.

**PoC:** `test_PoC_TierBoundaryFrontrun` (Lampiran A) — korban mengutip 10 share
= 10 USDT saat 2.490 terjual; penyerang mengambil 10 share Tier 1 terakhir;
transaksi korban dieksekusi seharga 15 USDT (+50%) dengan pass Tier 2. ✅ PoC
lolos.

**Rekomendasi (kontrak immutable — mitigasi di frontend):**
- Frontend harus membaca `sharesSold()` sesaat sebelum mint dan menampilkan
  peringatan keras bila pembelian melewati/mendekati batas tier; tampilkan
  harga *aktual saat eksekusi* (bukan kutipan lama).
- Anjurkan user tidak mint dalam ±10 share dari batas 2.500/6.000 tanpa
  memeriksa ulang.
- Untuk deploy berikutnya: tambahkan parameter `maxTotalPrice` (revert bila
  `quote(amount) > maxTotalPrice`).

### L-2 — Tidak ada verifikasi jumlah USDT yang benar-benar diterima: token fee-on-transfer akan membuat graduation gagal (saat ini hipotetis — USDT BSC asli TIDAK ber-fee)

**Lokasi:** `src/KongSale.sol:325` (`safeTransferFrom` di `mintPass`),
`:366-380` (`graduate()`), `:470-478` (`sweepUnclaimed`)

**Penjelasan:** `mintPass` mencatat `totalRaised += totalPrice` berdasarkan
jumlah *nominal*, tanpa memeriksa saldo USDT sebelum/sesudah transfer. Bila
token pembayaran memungut fee transfer, saldo aktual sale akan selalu lebih
kecil dari `totalRaised`. `graduate()` menghitung porsi likuiditas/treasury
dari `totalRaised`, sehingga transfer treasury akan revert karena saldo kurang
→ graduation gagal total dan tidak bisa diulang sampai seseorang mendonasikan
selisihnya dari luar (tidak ada mekanisme in-protocol). Refund pun akan
kekurangan dana untuk pendaftar terakhir.

**Dampak saat ini: NIHIL (hipotetis).** Token USDT BSC asli
(`0x55d398326f99059fF775485246999027B3197955`) diverifikasi lewat ABI Sourcify
(19 Nov 2026): fungsi-fungsinya hanya BEP-20 standar + `mint`/`burn`/`owner`
— **tidak ada fungsi fee, pause, atau blacklist**. Asumsi kode terhadap token
ini benar. Temuan ini dicatat sebagai defense-in-depth.

**PoC:** `test_PoC_FeeTokenBricksGraduation` (Lampiran A) — mock USDT ber-fee
1%: setelah mint 10 share, `totalRaised` = 10 USDT tapi saldo sale 9,9 USDT;
pada skenario sold-out, `graduate()` revert (treasury butuh 3.150 USDT, sisa
saldo 2.992,5 USDT). ✅ PoC lolos.

**Rekomendasi:** untuk deploy berikutnya, verifikasi jumlah diterima
(`balanceAfter - balanceBefore`) pada `mintPass` dan pakai jumlah aktual itu
untuk akuntansi; atau batasi token pembayaran ke token yang sudah diaudit
perilaku transfernya (seperti yang sudah dilakukan di sini — pertahankan
praktik verifikasi ABI token pembayaran sebelum deploy).

### L-3 — Interaksi graduation dengan router PancakeSwap asli tidak pernah diuji (MockRouter selalu sukses dengan jumlah exact)

**Lokasi:** `test/mocks/Mocks.sol` (`MockRouter`), `test/KongSale.t.sol`
(`test_GraduationSplit`)

**Penjelasan:** `MockRouter.addLiquidity` hanya menarik jumlah yang diminta
persis dan mengembalikan sukses. Ia tidak mensimulasikan: pembuatan pair,
logika jumlah optimal, pemeriksaan `deadline`, atau kasus revert router.
Artinya pemanggilan eksternal paling konsekuensial (12.600 USDT + 250M KONG)
hanya diuji terhadap stub — termasuk asumsi bahwa `amountAMin = 0 /
amountBMin = 0` aman dan `deadline = block.timestamp` diterima router.

**Dampak:** rendah — pola `addLiquidity` yang dipakai adalah pola standar
UniswapV2 dan router PancakeSwap sudah battle-tested; risiko utamanya adalah
asumsi yang belum teruji (mis. perilaku bila pair sudah ada — lihat M-1).

**Rekomendasi (bisa dilakukan sebelum 1 Des, read-only, tanpa tx mainnet):**
tulis fork test BSC mainnet yang men-deploy sale, mengisi 10.000 share,
lalu memanggil `graduate()` melawan router PancakeSwap V2 asli
(`0x10ED43C718714eb63d5aA57B78B54704E256024E`) dan assert saldo pair
+ event + `graduated`. Polanya sudah ada di `KongDecimalsForkTest`.

## Temuan Informational

### I-1 — Nama error menyesatkan: `RefundWindowClosed` dipakai saat jendela BELUM tutup

**Lokasi:** `src/KongSale.sol:168` (deklarasi), `:470` (dipakai di
`sweepUnclaimed`: `if (block.timestamp < refundDeadline()) revert
RefundWindowClosed();`)

**Penjelasan:** `sweepUnclaimed()` revert dengan `RefundWindowClosed` justru
ketika jendela refund *masih berjalan*. Nama yang benar adalah
`RefundWindowNotClosed`. Tidak ada dampak fungsional (test menegaskan perilaku
ini), tapi menyesatkan integrator dan auditor berikutnya.
**Rekomendasi:** ganti nama di deploy berikutnya.

### I-2 — DESIGN.md salah menyatakan durasi vesting: "lunas 12 bulan" vs kode 455 hari

**Lokasi:** `docs/DESIGN.md` §4 ("Vesting 12 bulan (cliff 3 bulan)") dan §7
("vested (cliff 3 bulan, lunas 12 bulan)") vs `src/KongVesting.sol:37-40`
(`CLIFF = 90 days`, `DURATION = 365 days`).

**Penjelasan:** kode melepaskan penuh pada `start + 90 + 365 = start + 455 hari`
(~15 bulan). README keputusan #1 sudah mendokumentasikan resolusi ambiguitas
ini (12 bulan *setelah* cliff), tapi DESIGN.md — dokumen otoritas desain yang
baru saja dipublikasikan di GitHub — masih menulis 12 bulan. Pembaca DESIGN.md
(termasuk penerima treasury/tim) akan mengharapkan unlock 3 bulan lebih awal
dari kenyataan.
**Rekomendasi:** perbaiki kata-kata DESIGN.md §4/§7 menjadi "cliff 3 bulan,
lalu linear 12 bulan (lunas 15 bulan setelah graduation)". Tidak ada perubahan
kontrak yang dibutuhkan — keputusannya sendiri sah dan terdokumentasi di README.

### I-3 — "Maks 10 pass per Agent ID" (DESIGN.md) vs cap per wallet di kode

**Lokasi:** `docs/DESIGN.md` §2/§7 vs `src/KongSale.sol:324`
(`mintedByWallet[msg.sender]`).

**Penjelasan:** kode membatasi 10 pass per *alamat wallet*, bukan per Agent ID.
Wallet dengan 2 Agent ID tetap hanya dapat 10 (lebih ketat); seseorang dengan
2 wallet + 2 Agent ID dapat 20 (lebih longgar dari aturan tertulis). Cap
per-manusia tidak bisa ditegakkan on-chain; implementasi per-wallet adalah
pilihan praktis yang benar dan sudah didokumentasikan di README ("cap counts
minting, not holding").
**Rekomendasi:** selaraskan kata-kata DESIGN.md menjadi "maks 10 pass per
wallet".

### I-4 — Storage mati: immutable `community` (dan `team` setelah konstruktor) tidak pernah dibaca

**Lokasi:** `src/KongSale.sol:117-118` (`team`, `community`).

**Penjelasan:** `community` disimpan tapi tidak dipakai fungsi apa pun
(transfer 50M komunitas dilakukan deployer langsung, bukan oleh kontrak).
`team` hanya dipakai di konstruktor sebagai beneficiary vesting. Tidak ada
dampak keamanan; hanya biaya deploy yang sedikit lebih besar.
**Rekomendasi:** hapus di deploy berikutnya, atau pertahankan sebagai
dokumentasi on-chain (keputusan sadar, bukan bug).

### I-5 — Dana yang dikirim langsung ke kontrak sale (donasi/salah kirim) tidak bisa dipulihkan setelah graduation

**Lokasi:** `src/KongSale.sol:469-478` (`sweepUnclaimed` hanya pra-graduation,
hanya USDT).

**Penjelasan:** USDT yang ditransfer langsung ke sale (bukan via `mintPass`)
tidak masuk `totalRaised`: saat graduation ia tertinggal di kontrak dan
terkunci permanen (tidak ada rescue; sweep hanya berlaku bila gagal).
Token lain/ETH yang salah kirim juga terkunci (ETH biasa akan revert karena
tidak ada `receive`, kecuali via `selfdestruct`/coinbase — dapat diabaikan).
Ini konsekuensi desain tanpa admin, bukan bug.
**Rekomendasi:** cantumkan peringatan "jangan kirim token langsung ke alamat
sale" di halaman mint dan README.

### I-6 — Gambar tier di `tokenURI` bergantung pada ketersediaan GitHub Pages

**Lokasi:** `src/KongMintPass.sol:128-151` (`tokenURI`), URI gambar di
konstruktor (immutable).

**Penjelasan:** metadata JSON on-chain (base64), tapi field `image` menunjuk
ke `https://zainumq.github.io/kong/kong-pass-tier*.jpg`. Bila Pages down atau repo
dihapus, gambar pass hilang (metadata tetap terbaca). Desain sudah mengakui
gambar bersifat eksternal.
**Rekomendasi:** untuk koleksi berikutnya, pin juga artwork ke IPFS/Arweave;
untuk v3, jaga repo GitHub tetap publik (sudah menjadi rencana).

### I-7 — Referral wash-trading antar wallet sendiri dimungkinkan (by design, terbatas pool)

**Lokasi:** `src/KongSale.sol:299-347` (aturan referrer).

**Penjelasan:** self-referral revert, tapi satu orang dengan dua wallet bisa
saling merujuk: wallet A beli pass, wallet B beli dengan referrer A → A
mendapat 3%. Ini kebocoran standar program referral, bukan exploit: penyerang
harus benar-benar membeli share (mengeluarkan USDT), dan total ekstraksi
dibatasi pool 15M (maks teoretis 14.548.200 KONG bila semua share kecuali
share #1 memakai referrer — tetap < 15M).
**Rekomendasi:** tidak ada tindakan; dicatat sebagai perilaku yang diterima.

### I-8 — Celah kecil cakupan test: jalur `Underfunded` dan sweep-pasca-graduation tidak diuji

**Lokasi:** `test/KongSale.t.sol`.

**Penjelasan:** tidak ada test yang men-deploy sale yang sold-out tapi
underfunded lalu menegaskan `graduate()` revert `Underfunded`; tidak ada test
yang menegaskan `sweepUnclaimed()` revert `AlreadyGraduated` setelah
graduation. Keduanya pemeriksaan satu baris yang secara manual sudah benar,
tapi belum terkunci oleh test.
**Rekomendasi:** tambahkan dua test singkat (murah) sebelum 1 Des.

## Diperiksa, tidak ada masalah

- **Reentrancy** — semua fungsi pengubah state yang memindahkan dana
  (`mintPass`, `graduate`, `claim`, `claimMany`, `claimReferral`, `refund`,
  `refundMany`, `sweepUnclaimed`, `release`) memakai `nonReentrant` + pola
  checks-effects-interactions (burn/zeroing sebelum transfer). Test
  `KongReentrancyTest` (4 test, token + router jahat) lolos. Jalur callback
  `_safeMint` → `onERC721Received` milik buyer juga aman: semua fungsi sale
  ter-guard dan `mint`/`burn` pass `onlySale`.
- **Access control** — `KongMintPass.mint/burn` dan `KongVesting.start`
  hanya bisa dipanggil sale (immutable). Tidak ada owner/admin/pause/withdraw
  di mana pun. `graduate`/`sweepUnclaimed`/`release` permissionless by design
  dan hanya bisa menguntungkan penerima yang sudah ditentukan (pool/treasury/
  beneficiary).
- **Matematika (diverifikasi manual + fuzz)** — batas tier 2.500/6.000
  konsisten di keempat view; total raise 2.500 + 5.250 + 8.000 = 15.750 USDT
  exact; klaim 150M + 175M + 160M = 485M = `SALE_ALLOCATION`; split graduation
  80/20 exact (12.600 + 3.150, tanpa dust karena treasury mendapat sisa);
  referral maks 4,5M + 5,25M + 4,8M = 14,55M < pool 15M (maks realistis
  14.548.200 karena share #1 tidak bisa memakai referrer); vesting linear
  dengan cabang akhir exact (tidak ada dust terkunci — `vested()` mengembalikan
  `total` penuh pada/lewat akhir). Tidak ada overflow (Solidity 0.8.24 checked;
  nilai maks ~1e26, jauh di bawah 2^256).
- **Desimal/satuan** — harga hardcode 1e18/1,5e18/2e18 cocok dengan USDT BSC
  18 desimal (bug v2 sudah diperbaiki; regresi `KongDecimalsTest` +
  `KongDecimalsForkTest` ada). Tidak ditemukan asumsi desimal/satuan lain yang
  salah: KONG 18 desimal konsisten di semua konstanta (`ether`), tier token
  60k/50k/40k konsisten antara `KongSale` dan `KongMintPass` (duplikasi
  konstanta — lihat catatan di bawah).
- **USDT asli** — ABI dari Sourcify: BEP-20 standar + `mint`/`burn`/
  `Ownable` (jembatan Binance). Tidak ada fee, pause, atau blacklist.
  `SafeERC20` dipakai di semua transfer (menangani token non-bool-return).
- **Race antar fungsi** — state saling eksklusif: mint butuh belum sold-out;
  klaim butuh graduated; refund butuh !graduated + dalam jendela; sweep butuh
  !graduated + lewat jendela. Tidak ada jalur ganda klaim/refund untuk satu
  pass (burn + `ownerOf` revert + `paidFor` dihapus).
- **Graduation gagal karena underfunded** — bila sale sold-out tapi tidak
  terdanai 750M, `graduate()` revert `Underfunded`, dan refund tetap terbuka
  setelah deadline (karena `!graduated`) — dana user tidak terkunci. (Pendanaan
  v3 terverifikasi lengkap on-chain.)
- **Front-running `graduate()`/`sweepUnclaimed()`** — tidak ada vektor
  pencurian: graduation menciptakan pool pada rasio tetap dan mengirim 20% ke
  treasury; sweep hanya ke treasury. Sandwiching pembukaan pool adalah risiko
  inheren peluncuran AMM, bukan bug kontrak (dan sudah diungkap di DESIGN.md
  §9 sebagai risiko harga pasca-graduation).
- **Gas/DoS loop** — `claimMany`/`refundMany` memakai array tak terbatas, tapi
  gas dibayar pemanggil sendiri; array terlalu panjang hanya membuat tx
  pemanggil itu gagal. Tidak ada DoS terhadap pihak lain. `quote()` loop
  maksimal 10 iterasi saat dipakai `mintPass`.
- **Vesting** — `totalAllocated() = balance + released` adalah pola standar
  OZ VestingWallet (donasi ekstra ke kontrak ikut vesting ke beneficiary
  dengan jadwal sama — perilaku terdokumentasi, bukan bug). `start()` sekali,
  hanya sale. Bila sale gagal, token vesting terkunci selamanya — by design
  dan sudah diungkap di dokumen.
- **KongToken** — ERC-20 OZ murni, supply tetap, tanpa mint/burn/owner.
  Tidak ada masalah.
- **Duplikasi konstanta tier** — `TIER*_TOKENS` di-hardcode di `KongSale`
  dan `KongMintPass` (dua sumber kebenaran). Nilainya cocok saat ini dan
  dikunci oleh test klaim; risiko pemeliharaan saja, bukan temuan aktif.

contract KongAuditPoCTest is Test {
    address internal treasury = makeAddr("treasury");
    address internal team = makeAddr("team");
    address internal community = makeAddr("community");
    string internal constant IMG1 = "https://kong.example/art/tier1.png";
    string internal constant IMG2 = "https://kong.example/art/tier2.png";

    function deploySale(address kong, address usdt, address router) internal returns (KongSale) {
        MockAgentID agentId = new MockAgentID();

    // PoC-1 (M-1): pool menyimpang -> 6.300 USDT terkunci di sale selamanya.
    function test_PoC_SkewedPoolLocksExcessUsdt() public {
        vm.warp(1_800_000_000);
        KongToken token = new KongToken();
        MockUSDT usdt = new MockUSDT();
        SkewedRouter router = new SkewedRouter();
        KongSale sale = deploySale(address(token), address(usdt), address(router));
        token.transfer(address(sale), 750_000_000 ether);

        vm.store(address(sale), bytes32(uint256(0)), bytes32(uint256(10_000))); // sharesSold
        vm.store(address(sale), bytes32(uint256(1)), bytes32(uint256(15_750e18))); // totalRaised
        sale.graduate();
        assertTrue(sale.graduated());
        assertEq(usdt.balanceOf(address(router)), 6_300e18);
        assertEq(usdt.balanceOf(address(sale)), 6_300e18); // terkunci
        vm.expectRevert(KongSale.AlreadyGraduated.selector);

    // PoC-2 (L-1): korban mengutip 10 USDT, membayar 15 USDT (+50%).
    function test_PoC_TierBoundaryFrontrun() public {
        vm.warp(1_800_000_000);
        KongToken token = new KongToken();
        MockUSDT usdt = new MockUSDT();
        MockAgentID agentId = new MockAgentID();
        MockRouter router = new MockRouter();
        KongSale sale = new KongSale(address(token), address(usdt), address(agentId),
            address(router), treasury, team, community, block.timestamp, IMG1, IMG2, IMG3);
        token.transfer(address(sale), 750_000_000 ether);
        uint256 n = 0;
        while (sale.sharesSold() < 2_490) {
            address b = address(uint160(0x60000 + (++n)));
            usdt.mint(b, 1_000_000e18);
            agentId.setBalance(b, 1);
            vm.prank(b); usdt.approve(address(sale), type(uint256).max);
            vm.prank(b); sale.mintPass(10, address(0));
        }
        address victim = makeAddr("victim");
        usdt.mint(victim, 1_000_000e18);
        agentId.setBalance(victim, 1);
        vm.prank(victim); usdt.approve(address(sale), type(uint256).max);
        assertEq(sale.quote(10), 10e18); // korban mengutip 10 USDT (semua T1)
        address attacker = address(uint160(0x70000));
        usdt.mint(attacker, 1_000_000e18);
        agentId.setBalance(attacker, 1);
        vm.prank(attacker); usdt.approve(address(sale), type(uint256).max);
        vm.prank(attacker); sale.mintPass(10, address(0)); // rebut 10 T1 terakhir

        vm.prank(victim); sale.mintPass(10, address(0));
        assertEq(balBefore - usdt.balanceOf(victim), 15e18); // membayar 15 USDT
        assertEq(sale.pass().tierOf(2_501), 2); // pass Tier 2, bukan Tier 1
    }

contract SkewedRouter {
    function addLiquidity(address tokenA, address tokenB, uint256 amountADesired,
        uint256 amountBDesired, uint256, uint256, address, uint256)
        external returns (uint256 amountA, uint256 amountB, uint256 liquidity) {
        uint256 usedB = amountBDesired / 2; // pool menyimpang: hanya pakai setengah USDT
        IERC20(tokenA).transferFrom(msg.sender, address(this), amountADesired);
        IERC20(tokenB).transferFrom(msg.sender, address(this), usedB);
        return (amountADesired, usedB, 1 ether);
    }
}

contract FeeUSDT is ERC20 {
    address public constant FEE_COLLECTOR = address(0xFEE);
    constructor() ERC20("Fee USDT", "fUSDT") {}
    function decimals() public pure override returns (uint8) { return 18; }
    function mint(address to, uint256 amount) external { _mint(to, amount); }
    function transfer(address to, uint256 amount) public override returns (bool) {
        uint256 fee = amount / 100;
        super.transfer(to, amount - fee);
        super.transfer(FEE_COLLECTOR, fee);
        return true;
    }
    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        uint256 fee = amount / 100;
        super.transferFrom(from, to, amount - fee);
        super.transferFrom(from, FEE_COLLECTOR, fee);
        return true;
    }
